# Course guardrail (every course on ihor.sh, every agent)

Each lesson is read by someone who knows only what the earlier lessons taught. Keep that true. You are not
writing "a lesson about a topic". You are writing the next step for a learner at one exact point on a path.

## The three rules

1. **No gaps.** Use only what earlier lessons in this course have taught (terms, notation, syntax, concepts), plus at
   most one or two new things that this change teaches explicitly. "They probably know it" doesn't count: name the
   lesson that taught it, and check that it really does.
2. **See it before naming it.** Start from a question the learner can almost answer, then a picture or widget they
   can play with. Words come after that, then formulas, then code. Ask for a prediction before every reveal.
3. **Fit it in; don't improvise.** New material goes where it belongs in the existing course. In order of preference:
   a. fix or extend an existing section;
   b. add a section, or an optional "deeper" box, to an existing lesson;
   c. add a new lesson, only when (a) or (b) would overload a lesson, and slotted into the existing order.
   Never teach the same thing twice. Link to the place where it's taught.

## Before you edit: the fit plan

Write this down before changing any content: in the course's PLAN.md for anything bigger than one section, or in
your reply and commit message for a small fix.

```
Topic:           what the learner can do afterwards, in one sentence
Already covered: every lesson and section that touches it, as file:line (from the search below)
Gap:             the specific missing piece ("the SVM dual form", not "SVMs")
Where it goes:   file and section, and which of 3a/3b/3c it is and why
Needs:           each term, symbol and piece of syntax it uses → the earlier lesson that teaches it (looked up, not recalled)
New here:        the 1–2 things taught for the first time, and how: picture → words → formula → code
Also touches:    index cards, course.json, glossary/notation/cheatsheet pages, cross-links, notebook, quiz
Verified by:     the commands you ran and the cold-learner read
```

**The search, every time:**
- `grep -ril -e "<term>" -e "<synonym>" -e "<abbreviation>" <course dir>` for the topic *and* its other names
  (IoU and "intersection over union"; bias-variance and "bias²"; kernel trick and RBF). Then **open every hit and read
  that section**. Lesson titles don't tell you what's inside.
- Look up every prerequisite where it's actually taught (for AI, use `lint.py --ledger <lesson>`). If it's taught
  *after* your lesson, or nowhere, then teach it first, in the earlier lesson where it belongs, and register it.
- If the search shows the gap is already covered, the plan becomes "link to it", or nothing at all.

## Teaching rules (every course)

- **One new idea per step.** It's a ramp, not a cliff: the first exercise is always the smallest one.
- **Purpose before mechanism.** Every section, widget and game opens by saying what problem it solves for the learner's
  goal (in the course's own terms), before any construction. A learner who can follow every step but can't say why the
  section exists has hit a gap. If a section only explains notation or satisfies curiosity, say so and make it optional.
- **Layers:** see it → say it (a one-sentence gist) → why it's true (an optional deeper box, 4–8 short steps) →
  where it breaks (a concrete counterexample with numbers) → where it's used. Nothing after an optional box may depend on it.
- **Intuition drills:** predict, then reveal; push to extreme cases; estimate before computing; check the theory
  numerically in code.
- **Forward references are pointers only** ("the next lesson shows how math writes this"). A preview of a later
  topic is labeled as a preview and is never an exercise.
- **Fix the ledger, not the symptom.** If a lesson needs something the path never taught, teach it in the earlier
  lesson where it belongs, so every later lesson benefits. Don't delete a good bridge just to silence a warning.
- **Keep the main read short.** If a lesson grows much longer than its neighbors, move depth into boxes or split it.
- **Widgets** work from the keyboard, at 390 px wide, and with reduced motion.
- **Use real data where it's natural** (NYC data, the site's own radio). Synthetic data is fine, but say so on the page.
  Don't force a city theme onto a topic where it would be fake.

## Truthfulness

- **Every number you quote comes from code you ran or a source you link.** Guessed numbers have been wrong here before.
- **Never invent** datasets, results, benchmarks, speeds, quotes or attributions. If you can't verify it, leave it out.
- **It must run where it will run.** AI lesson code runs in Pyodide in the browser (NumPy, pandas, scikit-learn,
  matplotlib; no PyTorch, no API keys, no hosted LLMs). In-browser models use transformers.js. Heavier work goes in the
  notebook (Kaggle/Colab). Radio code is the TypeScript that really runs the receiver.
- **Copy no copyrighted text or figures** (fast.ai, the ARRL Handbook, textbooks, course slides): write original
  explanations and link to the source. Famous course names (CS229, 3Blue1Brown) are inspiration, never the reason
  for adding something. The reason is a gap in this learner's path.

## Plans

- Plans live in the course's PLAN.md (`ai/PLAN.md`, `radio/course/PLAN.md`). Unplanned ideas go in `IDEAS.md` (local only).
- Every planned item has a filled-in fit plan. Never write "dependency risk: zero" or "no gaps" unless you checked each
  item, and then say what you checked.
- Keep it consistent: one name per file everywhere, and nothing in a summary box that the details don't cover.
- No counts that go stale ("all 167 OK"): name the command instead.
- Don't make product decisions on the side (unlocking or hiding stages, removing sections, renaming, restyling). Ask first.

## Done means

- The course's checks (in the table above) pass with 0 errors.
- **The cold-learner read:** read the page, and then the notebook, as someone who knows only the earlier lessons.
  Every place where you'd have to guess what's meant is a bug.
- The page renders at 390 px and at 1280 px with no horizontal scroll and no console errors.
- One step per commit. Stage only the files you changed: other agents work in the same tree, so never stage, revert
  or reformat their uncommitted files. Push, then deploy as the README says.
- The commit message says what the learner gets and what you verified, with the real numbers.
