Radio from scratch · Chapter 8

Chunks of a live stream

Before you startThis chapter uses the three steps so far:
  • Chapter 5: the mixer's running angle (the NCO)
  • Chapter 6: the filter's sliding bracket
  • Chapter 7: keeping every M-th output
It also peeks ahead at the FM demodulator (chapter 9), which needs the previous sample.

So far, every picture processed a recording: a fixed list of samples, start to finish. Live radio isn't like that. It never starts and never ends. The dongle hands over a chunk of samples about every 55 ms, and each chunk has to be processed and played while the next one is already arriving.

The obvious approach is to treat each chunk as its own little recording. It almost works, and the way it fails is something you can hear.

Hear the problem

With "nothing", the tone is a smooth wave straight through every pink chunk boundary, and it sounds like a clean whistle. Every other choice puts a glitch at every boundary, and you hear it as a buzz or a crackle repeating at the chunk rate (with 8 ms chunks, 125 times per second). Real radio uses ~55 ms chunks, so the clicks would come about 18 times a second, on top of the music. Unbearable.

What each step must remember

Each step needs a different, small piece of memory from the previous chunk:

  • The mixer needs its running angle (↩ ch. 5: the NCO). If it restarts at angle 0, its spinning arrow jumps to a new position at every boundary, and so does everything multiplied by it.
  • The filter needs the last few dozen samples of the previous chunk (↩ ch. 6: the sliding bracket). Its bracket reaches back in time: the first outputs of a new chunk depend on samples from the old one. Without them, the bracket is mostly averaging empty space (zeros), so the output sags towards zero until the bracket has filled up again.
  • The decimator needs to know where the next kept sample falls (↩ ch. 7). Chunks aren't a multiple of M long, so if a chunk ends 3 samples after the last kept one, the next chunk must start keeping at its own sample M−3, not at 0. Otherwise the spacing stutters.
  • The FM demodulator needs the previous sample, because it measures how far the arrow turned since then (chapter 9). For the first sample of a chunk, "then" is in the previous chunk.

The solution is unglamorous and complete: each step is a small object that keeps its memory between calls. Processing a chunk updates the memory; the next call carries on from it. Processing a whole file is then just processing one very big chunk, so a single implementation serves both.

How would you prove that the memory is handled perfectly, without listening for clicks?

Feed the same signal both ways, once as one big buffer and once as chunks of an awkward size (say 12 345 samples, so nothing lines up), and compare every output number. They must be identical, bit for bit, not just close. That's the test this site's receiver passes for every mode (see "In code" below).

The price of chunks: delay

Chunks also cost time. A chunk can't be processed until it has fully arrived, the filters add a little delay of their own (their output reflects the middle of their bracket, which is in the past), and the audio player keeps a small cushion of sound queued so that a late chunk doesn't cause a gap.

Smaller chunks mean less delay, but more overhead: every chunk costs a USB request, a function call per step, and a bit of bookkeeping. ~55 ms is a comfortable middle for listening. Two-way radio and live monitoring care about delay much more, and use smaller chunks.

In code

Here is where each step keeps its memory in src/dsp.ts. The mixer saves its angle at the end of every call:

let ph = this.ph;               // pick up where the last chunk left off
// … process this chunk …
this.ph = ph;                   // remember for the next chunk

The filter-and-decimator keeps the tail of the input (hist) and where the next kept output falls (next). It glues the remembered tail in front of each new chunk, so the bracket can reach back across the boundary:

const buf = new Float32Array(this.hist.length + x.length);
buf.set(this.hist); buf.set(x, this.hist.length);            // old tail + new chunk
// … compute outputs at positions next, next + m, next + 2m, … …
this.next += count * m - n;                                  // where the next kept sample falls in the next chunk
this.hist = buf.slice(buf.length - this.hist.length);        // keep the new tail

The FM demodulator remembers the previous sample (pi, pq). The test that proves it all works, from src/dsp.test.ts:

const whole = new Receiver(fs, 200e3, mode, bw).process(iq).audio;
const r = new Receiver(fs, 200e3, mode, bw);
for (let s = 0; s < iq.length; s += 2 * 12_345) parts.push(...r.process(iq.subarray(s, s + 2 * 12_345)).audio);
assert.ok(parts.every((v, i) => v === whole[i]));   // identical, not just close

Check yourself

Why does a filter that forgets its history produce a dip at each chunk edge?

Its bracket reaches back into the previous chunk. Without that data it averages zeros for those positions, so the first outputs are too small until the bracket is filled with new samples.

Your chunks are 55 ms long and something forgets at every edge. How often do you hear a click?

About 18 times per second (1000 / 55).

Why compare chunked and whole processing bit for bit, instead of "close enough"?

If the memory is handled exactly right, the arithmetic is literally the same operations in the same order, so the results must be identical. Any difference at all means something at a boundary is wrong, even if it's too small to hear yet.
