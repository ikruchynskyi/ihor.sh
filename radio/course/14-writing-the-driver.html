Writing the driver

Before you startThis chapter builds directly on:
  • Chapter 13: control transfers and register addressing
  • Chapter 12: the chips, the IF and the PLL
  • Chapter 8: why the stream must never stall

A driver sounds mysterious. For this dongle it's two things: a list of register writes in exactly the right order, and the knowledge of what each one means. Chapter 13 showed single messages. This chapter shows the whole conversation, every message our driver sends from "open" to "close", and then the code that produces it.

Everything the driver says, in order

Below, the real driver from this site runs through a typical session (open, set the sample rate, tune to 98.45 MHz, set the gain, close) against a pretend dongle: an object that accepts every write and answers like a real one. Every control transfer is recorded and decoded into words. It happens right now in your browser; open each phase:

Some things to look for:

  • RTL2832U start-up (the biggest phase): power on the demodulator, reset it, then write the 20 resampler-filter coefficients one by one (chapter 3's anti-aliasing filter), switch to SDR mode, and turn off everything that was meant for TV.
  • Find the tuner and set up for it: "start reading at register 0x00", and the answer 0x69: that's how the driver knows it's an R820T. Then the RTL2832U is told about the tuner's 3.57 MHz IF.
  • Tuner start-up: four bulk writes of the 27 start-up values (7 at a time, the I2C bridge's limit), then the IF filter calibration: the PLL goes to 56 MHz, a trigger bit is pulsed, a code is read back.
  • Tune: notice registers 0x14, 0x15 and 0x16 (the PLL integer and fraction from chapter 12) and the status read that checks the lock bit.
  • Almost every tuner phase starts with "I2C repeater on" (demod register 0x01 = 0x18) and ends with it off (0x10).

Why does the driver write 20 filter coefficients into the RTL2832U at start-up?

The chip decimates the converter's samples before sending them, and decimating without filtering first lets other stations fold in on top of yours (chapters 3 and 7). Those 20 numbers are that anti-aliasing filter.

How anyone knows what to write

Predict: neither chip has a public datasheet. How does anyone know which registers to write?

  • The makers publish it under license
  • The open-source community recorded and reverse-engineered what TV software sent
  • Trial and error by each driver author
Captured USB traffic, leaked reference code and experiments, pooled since 2012, when people found the undocumented SDR mode.

Neither chip has a public datasheet. The knowledge in the trace above was pieced together over years by the open-source community: people recorded what Windows TV software sent to these sticks, studied leaked reference code from the chip makers, and experimented. In 2012 they discovered the RTL2832U's undocumented "SDR mode" that ships raw samples, which is what turned a $20 TV stick into a radio receiver. The results live in osmocom's librtlsdr and the Linux kernel's drivers; our driver is a fresh TypeScript implementation of that shared knowledge.

That's also why the trace decoder above can name every register: the names come from the same community work. Writing a driver for a chip without a datasheet means reading other drivers carefully, and testing a lot.

Testing a driver

How could a test check that an FM receiver works on a real station, without anyone listening?

Look for something every FM stereo station sends and that's easy to measure: the 19 kHz pilot. If the demodulated audio has a strong, steady 19 kHz tone, the whole chain from USB to demodulator works.

Hardware code is hard to test, because the hardware isn't always there and doesn't always behave. This driver is tested at four levels, each catching different mistakes:

  1. A fake chip (chapter 12's script): the tuner driver runs against a pretend I2C bus that records writes. Checks: does the driver write the PLL values the math says it should?
  2. A recorded trace (this chapter's script): the whole driver runs against a pretend dongle. Checks: does every message have a known meaning, in a sensible order? (All 216 do.)
  3. The real dongle, with a test that doesn't need ears (npm run hw-test): capture from a real station and check that our FM demodulator finds the 19 kHz stereo pilot (↩ ch. 9). It can only be there if tuning, sample rate and I/Q handling are all right. It measures the real sample rate too, to catch dropped data.
  4. Abuse: open and close the dongle six times in a row, fast. This caught the nastiest bug.

The bugs we actually hit while building this driver, all now handled:

  • A string the dongle can't serve. Its configuration has a name that its firmware returns broken. Browsers don't care, but Node's USB package crashed reading it. Fix: don't ask for it.
  • A false alarm. A throughput test reported 2.307 million samples per second instead of 2.4, which looked like lost data. The timer had included closing the device. Lesson: check the measurement before the thing measured.
  • A dongle that ignores you. Reopened quickly after closing, the chip sometimes stalls its first commands. librtlsdr's fix is a USB reset. But on macOS the reset makes the dongle disappear and reappear as a new device, so the driver now finds it again and starts over.
  • Registers that stall. Writing a demodulator register while the demodulator is powered down stalls (chapter 13's lab hit this). Order matters: power first.
  • A stuck tuner. Once, after many resets, the tuner's analog side stopped passing any signal: every byte was 126–129, even in other software. Its digital side still answered 0x69. Only unplugging it (cutting its power) fixed it. Some states can't be reached from software at all.

In code

Recording a trace is a small trick worth knowing: wrap the device in a proxy, an object that passes every call through to the real one but writes it down first (src/course/trace.ts):

return new Proxy(dev, {
  get(t, k) {
    const v = t[k];
    if (k === "controlTransferOut") return async (s, data) => {
      log.push({ phase: phase.name, dir: "out", value: s.value, index: s.index, data: [...new Uint8Array(data)] });
      return v.call(t, s, data);                    // then do the real thing
    };
    // … the same for controlTransferIn, recording the answer …
    return typeof v === "function" ? v.bind(t) : v;
  },
});

The driver never knows it's being watched. Try it yourself: node course/code/ch14.ts prints the trace, phase by phase:

Check yourself

Why does nearly every tuner operation start with demod register 0x01 = 0x18?

That switches on the I2C repeater, the gate between the RTL2832U and the tuner's I2C wires. It's switched off again (0x10) afterwards so stray traffic can't reach the tuner.

Why does the tuner driver keep a copy of every register it writes?

Most of the chip's registers can't be read back. To change a few bits, the driver needs to know the rest of the byte, so it keeps its own copy. (Engineers call it a "shadow" register, which has nothing to do with chapter 1's shadows.)

How can you test that tuning works without listening to anything?

Tune to a stereo FM station and check that the demodulated signal contains the 19 kHz pilot. Wrong tuning, a wrong sample rate or mixed-up I/Q would all destroy it.
