The network source

Before you startThis chapter uses:
  • Chapter 13: bulk streams and chapter 8: chunks
  • Chapter 7: decimation (a narrow slice needs far fewer samples)
  • Chapter 1: the two shadows (what goes wrong if I and Q swap places)

One antenna on a rooftop can serve everyone. This site does exactly that: the dongle is plugged into a computer, a small server (server.ts) runs our driver there, and your browser receives the same bytes over the network that it would get over USB. Everything from chapter 3 on works unchanged.

Almost unchanged. A network is not a USB cable, and three new problems appear: data arrives in pieces of random size, there's far less of it to go around, and many people want the same dongle at once.

Pieces of any size, and the mirror-image ghost

The server sends neat 256 KiB chunks. The network doesn't care: it delivers whatever has arrived, in pieces of any size, including odd sizes. Measured on this site's server: 48 of 120 pieces had an odd number of bytes. Remember the byte order: I, Q, I, Q… (↩ ch. 3). After an odd-sized piece, the next piece starts with a Q.

If the page decodes each piece on its own, assuming the first byte is always an I, half the stream ends up with I and Q swapped. Untick the box to see what that does:

Swapping the two shadows (↩ ch. 1) mirrors every arrow: counter-clockwise becomes clockwise, so +200 kHz shows up at −200 kHz too. Every station gets a ghost twin on the opposite side of the center, just as strong. A beginner's network receiver often has exactly this bug, and it's baffling until you know to look for it.

The fix is simple: collect pieces into a buffer, and only hand on an even number of bytes, keeping any leftover byte for the start of the next batch.

There's much less bandwidth to go around

Inside a computer, 4.8 MB/s is nothing. Across the internet, it's a lot, and a server has to send it to every listener separately. A typical home connection uploads 10–40 megabits per second (1–5 MB/s). Slide the number of listeners:

Sending the whole band (what this site's server does today, fine inside your home) runs out after a listener or two. The rungs below it are everything you've learned, used to save bandwidth:

  • Send a slice: the server mixes each listener's station to the center, filters and decimates (chapters 5–7), and sends only that. A 48 kHz slice is 20× smaller than the whole band and still contains everything for AM, narrow FM or SSB. The listener's browser does the demodulation (chapters 9–11), so they can still see their slice's waterfall and switch modes instantly.
  • Send finished audio: about the same size as a narrow slice (both are 48 000 pairs or samples of numbers per second), but the listener can no longer see or retune within the signal; every change needs a round trip to the server. That's why sending the slice is usually the better deal.
  • Compress the audio (with a codec like Opus, what video calls use): tiny, but it adds delay and processing.

Public web receivers such as KiwiSDR and OpenWebRX send each listener their own slice plus a low-resolution waterfall of the whole band. That's the plan for this site's public version too.

One dongle, many listeners

A dongle has one center frequency and sees one slice of the band. Every listener must stay inside it, each with their own window:

For each listener, the server runs its own mixer, filter and decimator: a channelizer. That costs computing power per listener: at 2.4 MS/s with a 70-weight filter, roughly 350 million multiply-adds per second each (↩ ch. 6), divided by the decimation (↩ ch. 7). Servers with many listeners use a trick: one big FFT (↩ ch. 4) already splits the band into thousands of narrow slices at once, and each listener's slice is assembled from the pieces they need.

One more server-side rule from this site's server.ts: if a listener can't keep up, the server skips chunks for them instead of storing them. Storing would make that listener's delay grow forever; skipping costs them a click but keeps everyone else unaffected.

In code

The server (server.ts, Node's built-in HTTP): one dongle, many listeners, and skipping instead of storing for slow ones:

function fanOut(chunk) {
  for (const res of clients) {
    if (congested.has(res)) continue;                      // this listener is behind: skip, don't pile up
    if (!res.write(chunk)) { congested.add(res); res.once("drain", () => congested.delete(res)); }
  }
}

The browser side (src/remote.ts): read pieces, gather at least 64 KiB, hand on an even number of bytes, keep the leftover:

const { value, done } = await reader.read();               // a piece of any size
pending.push(value); size += value.length;
if (size < MIN_CHUNK) continue;
const even = size & ~1;                                   // round down to whole I/Q pairs
// … copy `even` bytes out, hand them on …
pending = size - even ? [lastPiece.subarray(-1)] : [];    // the odd byte starts the next batch

The API (three endpoints, documented in the build guide): GET /api/state, POST /api/tune, GET /api/stream. Browsers can't open raw network sockets, so the standard rtl_tcp protocol many SDR apps use isn't available to a web page, which is why our server speaks plain HTTP.

With pairs split, the ghost is exactly as strong as the station: there's no way to tell which one is real.

Check yourself

Why does an odd-sized network piece cause ghost stations?

The next piece starts with a Q byte. Read as an I, it swaps the two shadows, which mirrors every station to the opposite side of the center.

Ten listeners, each sent the whole band at 1.024 MS/s. How much upload does the server need?

2 MB/s each, so about 20 MB/s (160 Mbit/s): far more than most homes have.

Why does the server skip chunks for a slow listener instead of saving them for later?

Saved chunks would make that listener fall further and further behind, with ever-growing delay and memory. Skipping costs them a moment of sound but keeps them live, and doesn't slow anyone else down.
