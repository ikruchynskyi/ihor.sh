AI from scratch · Chapter 8

Agents

A language model only writes text: it predicts the next word (chapters 5 and 7). An agent is that same model put in a loop where some of what it writes is a request to do something, like look up trains, search the web or plan a trip, and the result is fed back for it to read. Blip, the little robot in the corner of this page, is one. This chapter opens it up.

1. The loop

your question + page + the list of tools
↓
model writes either a final answer  or  a tool call: subway_arrivals({"station": "Union Sq"})
↓ if a tool call
our code runs the tool → the result (JSON) is added to the conversation → back to the model
↓ when it answers (or after 4 rounds)
final answer

The model never touches the subway feed itself. It writes a structured request; ordinary code (the same server that runs this site) does the work and hands back data. The model's whole job is deciding which tool, with what arguments, and then reading the result correctly. Training taught it to write tool calls in a strict JSON format, the same way it learned to write sentences.

3. Watch Blip work

Ask something and see every step: the tool calls it decides to make, what each tool returned, and the answer it writes from them. Blip runs on a small model on a Mac mini here, so give it about ten seconds.

The trace shows up here.

Check its work. Compare the answer with the tool results above it. Small models sometimes misread a result: say "0 minutes" when the data says 6, or round a number wrong. The tool call was right and the data was right, but the last step, reading, went wrong. That's why serious agents keep the evidence next to the answer, and why the next section matters.

4. What goes wrong, and the guardrails

Loops. A model can keep calling tools forever, or call the same one again and again. Blip gets at most 4 rounds; after that it must answer with what it has.

Prompt injection. Tool results are text from the outside world: a web page, an event listing, a store's description. Any of it can contain instructions aimed at the model. One of these three search results is an attack. Which?

The defenses are boring and essential: tell the model in its instructions that tool output is data, never instructions; give tools the least power needed (Blip's tools only read; none can buy, send or delete); check arguments in code before running anything; and keep keys on the server, never in what the model sees. On this site the API also only answers the site's own pages, with per-visitor limits.

Bad arguments. The model might ask for station "Unoin Sq" or a date in the wrong format. Tools should validate inputs and return a clear error the model can recover from, not crash.

5. Evals: measuring an agent

"It seemed to work when I tried it" isn't a test. An eval is a fixed set of questions with checkable expectations, run every time you change the model, the prompt or a tool description. Here's a tiny one for tool choice: does Blip pick the right tool for each question? Run it (four live questions, about a minute).

Real eval suites have hundreds of cases and check more than tool choice: did the answer match the data, did it refuse what it should refuse, did it stay under the step limit. They're how you know whether a new model or a reworded tool description made things better or just different.
